# 天依非 Agent 系统综合评估与 DS 连接诊断

作者：Codex。核验日期：2026-10-04（北京时间）。对象：当前已实装的天依，不是路线图中的理想版本。

本报告与 [Agent 能力全景评测](AGENT_CAPABILITY_ASSESSMENT_2026-10-04_CODEX.md) 配套，供所有者决定下一阶段重点。前者回答“能否可靠完成任务”，本文回答“人物、演出、声音、界面、常驻、数据与交付处于什么状态”。不以主观完成百分比代替验收，不把本机可用等同于跨机器产品化。

核验基线：MVP `49936dd42844408d6229eac0ef80c8347a94c084`；配套 TTS `3814b4c9d32bb17c3638cf851e5649d9c7d17fa7`。本轮仅诊断、测试与文档，不修改运行源码、密钥、模型、动作或数据库，不重启/终止现有天依，不发送邮件，不注入生产故障。Claude、zcode、所有者和 Codex 的原有贡献归属保持不变。

## 1. 决策摘要

**当前已经是能够在本机使用的有形象、有声音、有演出的桌宠 MVP；尚不是对任意动作、网络、硬件和新机器都可靠的成品。**

- 外观最成熟：默认外观 **1.4**，独立表情修订 **1.0**。五官更清楚是材质线索增强，不是鼻子几何重建；官模网格、骨架、比例没有因此改变。
- 动作是“小型已验收动作库”：保守待机、倾听、思考、退出告别已有交付。复杂衣发接触仍靠动作约束和逐条适配，**没有完成通用全身防穿模系统**。
- 语音公共链路已经实现并有历史真实人声验收；本次 Core、TTS、唤醒就绪。剩余风险主要是设备/休眠/网络及错误可见性，不应把所有“不说话”都归为 TTS 崩溃。
- 当前新增的 DS 报错是主脑请求的通用传输错误。**本次4次独立请求全部成功，当前密钥/模型配置有效；截图发生时的精确网络原因尚不能从现有证据还原。** 未实施“修复”，不能宣布这次偶发故障已彻底根治。
- 界面满足基本互动，但能力状态、可操作错误提示、授权确认与任务过程的可见性不足。历史会话界面不等于结构化记忆审阅界面。
- 源码与现用声线已有分仓备份；官模/运行动作按所有者选择仍只留本地。**公开仓库不是完整离线安装包**，新机器、无 NVIDIA 和 macOS 等效体验仍待验证。

建议当前优先顺序：Agent 授权/执行真实性阻断项 → DS 故障可诊断与语音状态可见 → 有限范围长稳/设备验证 → 小幅低接触动作；不建议再先做一轮大规模换模或无边界物理重写。

## 4. 建模、画质和表情：究竟改了什么

### 4.1 模型外观版本不是同义于网格重建

| 版本 | 已接受的实际变化 |
|---|---|
| 1.0 | 正常比例基线 |
| 1.1 | 相机光轴、高清透明画布及抗锯齿 |
| 1.2 | Toon调色、降低过曝、受光层次 |
| 1.3 | 柔和Burley/低强度GGX材质精修；伴随保守待机与F12高清输出 |
| 1.4 | 脸部增加鼻、唇、耳内材质线索；继承其余1.3外观 |

本次 `verify-model-versions.ps1` 对五版全部返回 `MODEL_VERSION_OK`，索引 `current=1.4`；校验的是档案文件/资源契约及运行提交存在。**不是本次实际启动了五个旧版，也不保证旧版所有未来依赖都齐备。** 1.4起有独立运行支持资源快照，1.0–1.3仍受旧清单边界限制。

官模当前128,621,144字节，SHA-256仍为 `DF55806D343D149B41C20D0EF074373CAFCA2379212FD8691E998EA6CDDC6E4A`。`model_look_v14.gd` 仅为face材质增加next pass；当前运行时代码默认1.4，运行进程没有外观版本覆盖变量。源Blender751骨与Godot运行703骨是不同阶段计数，不能把两者之差当作本轮删骨。

表情是另一条修订轴：`emotion_presets.gd` 独立于外观版本。增强惊讶、生气、流泪不等于产生模型1.5。历史兼容验收包含122组材质/表情对照、180帧口型，以及后续表情组合/清除/恢复门禁；本次未重新做这些GPU渲染。

### 4.2 下一步真正有意义的视觉方向

1. 在用户日常显示尺寸下检查表情辨识度、视线和眨眼节奏，优先演出而不是无限加亮或放大五官。
2. 新动作先改善过渡、手臂轨迹和衣发接触，避免只看首尾静帧。
3. 若要做画质自适应，先测完整帧耗时、显存与多屏/DPI；F12单张高清PNG不是实时高清录像能力。
4. 派生高清纹理、发片边缘专项与通用二级物理仍是候选，不算现有成品。

下一正式外观版本应在获批后分配1.5，不覆盖1.4。没有证据需要目前直接换一个官模。

## 5. 动作与物理：可用范围必须说清楚

当前注册五项资源：idle、pirouette、listen、think、farewell。前四项由普通动作系统管理，farewell为退出专用；**五个资源不等于五种都通过自然无穿模验收**。尤其pirouette仍是历史旋转压力动作。

当前管线已经能把视频中的动作意图转成可用角色动画，但包含骨骼重定向、固定FK轨迹、手型/接触人工适配及最终烘焙。思考动作的辫子曲线只针对该动作制作；运行时不调用离线 `strand_physics.gd` 作为全局物理引擎。

真人身体不相交，不代表换成不同臂长、裙型和长辫子的角色后不相交。应分别验收：动作还原、关节自然、真实可见网格接触、过渡/打断、衣发回位。单个代理距离为正、骨骼测试通过、某个旋转帧正常，都不能替代这些验收。

现阶段最划算的是新增低接触动作：轻点头、小幅摇头/侧看、肩外侧短挥手、轻微呼吸/重心变化。贴裙、叉腰、抱臂、深蹲、大转身和持续手脸接触的成本高得多。若重新启动物理专项，应先定义明确动作域和自然度标准，独立验证，不能把旧实验直接搬回主仓。

## 6. 语音：已经闭环的部分与仍有边界的部分

### 6.1 实际链路

```text
唤醒/按键录音 → STT → 主脑/工具 → 回复文本
                                    ↓
上线/空闲/工作解说/告别台词 → 公共播报 → GPT-SoVITS → WAV
                                                    ↓
                                      Godot播放 → 分片回执 → 完成
```

上线、空闲、问答回复、下线告别已经是现有场景，不需要重新做四套TTS。未来新场景应调用公共播报入口，新增台词/触发策略并测试优先级、中断和完成状态，而不是再开一个语音服务。

### 6.2 已解决的具体工程问题

依据 [TTS专项记录](TTS_REPAIR_STATUS.md) 与当前代码，已实现：

- 运行期sidecar/看护恢复，绑定Godot会话代际，按PID/创建时间及路径确认归属；不广泛结束python进程。
- 真实模型预热完成才报告ready；健康失败短缓存，避免恢复后仍长时间认为不可用。
- STT及声线自检使用已有离线Whisper缓存，避免每次加载意外依赖外网下载。
- 对可重试合成失败有限等待，只恢复未播放片段；旧回复取消后不得迟到插播。
- `playbackId`回执、去重补送、明确未播失败后的重合成；超时不假装播完。
- 主动场景成功播放后才进入冷却；空闲提醒不能抢占思考/工作/待播回复。
- 告别台词使用独立稳定WAV缓存并预解码到Godot；动画与语音共同完成再正常退出。

这些是实装的软件行为，不只是测试脚本。声线训练成果属于所有者；Claude/zcode既有场景与客户端基础保留，Codex补生命周期、恢复与播放确认。

### 6.3 本次观察与历史实测不要混用

2026-10-04 11:00左右，本次只读检查：Core `/health/live`正常、avatar连接1；`tts.available=true`、播放协议2、告别缓存3条；wake运行且未暂停、有非零输入峰值；sidecar `phase=ready, device=cuda, consecutiveFailures=0`，合成计数9。进程启动记录约02:25。**进程仍在运行不证明这段时间每次请求都成功，也不是新的8小时持续听感验收。**

历史已完成的真实声线恢复约51–60秒，另有四场景实际Godot非零音频总线输出、组合进程故障及所有者“倾听和语音回复都正常”的确认。本次没有让用户重新录音或重做真实GPU故障注入。

现在观察到的“没有识别到清晰语音”发生在STT阶段；“无法连接deepseek API”发生在主脑阶段。TTS即使健康，也不能合成一个尚未生成的回答。**窗口在线、TTS就绪、主脑可用、最终声音到扬声器，是四个不同条件。**

### 6.4 仍不应宣称完成的保证

- 首次加载/故障重载存在等待；并非人物刚出现的每一个瞬间都已经可说话，需以 `Voice ready` 和实际链路为准。
- 休眠、断电、系统静音、设备拔插/驱动假死、显存持续不足、模型缺失和云API故障不能靠TTS看护消除。
- 最外层看护被外部终止后，已验证的是原CMD能补回，不是无限层自动复活。
- Core被强杀前尚未持久化/下发的任务，不具有完整现场恢复保证。
- 未完成24小时全链路长稳和完整声卡/睡眠唤醒矩阵；不把其未做说成已做，也不擅自开启长期监听。
- 自检阈值0.9是配置/筛选策略，不是用户听感准确率、每句识别准确率或永不出错保证。

因此语音线可以转入维护，但应保留有限设备回归与可见状态，不能承诺“以后任何场景完全无需验证”。

## 7. 界面、启动、运行环境和交付

### 7.1 界面

Godot是主体，Tauri只是可选调试/设置壳；开发agent不是运行依赖。当前已有角色拖动/缩放、透明画布、互动菜单、聊天浮层、历史会话及工具活动卡、三档投入度与语音入口。三档投入度不应理解为三个不同权限等级。

主要体验缺口：不同服务故障在界面上缺少清晰分层，用户难以判断“没听到”“正在识别”“主脑请求失败”“语音恢复中”。当前报错正说明这种成本。建议健康提示至少区分录音/STT、主脑、工具、TTS、播放器；不是把全部失败改成一个模糊红点。

授权确认中心、事实记忆审阅/编辑与更完善任务进度仍待做。不能把聊天记录页的删除按钮视为已经能够可靠删除某条长期事实，也不能用美化工具卡解决底层伪成功回执。

### 7.2 启停与资源

唯一正常入口保持 `start-anime-agent.cmd`。本次18项启动逻辑、13项TTS生命周期逻辑通过，测试替换了进程/端口边界，不触碰用户窗口。历史专项另有真实CMD、多入口并发、快速关窗重开、Core/TTS故障和外部端口保护证据。

正常关窗与任务管理器强杀不是同一契约；外部程序占用端口时安全拒绝也不是启动器应当乱杀其他进程的理由。Windows登录自启仍按所有者决定暂缓。

本机本次只读硬件观察为RTX5060 Laptop、约8GiB显存。单次显存/利用率属于整机瞬时状态，未做各组件独占归因或长时间帧率采样，故不提供虚构的最低硬件或稳定60FPS结论。CPU语音能运行的历史试验不代表普通轻薄本能达到本机实时体验。

### 7.3 发布与换机

## 9. 本次 DS 连接失败诊断

### 9.1 已确定的事实

1. 截图是天依返回“无法连接 deepseek API”，另有独立STT提示。发邮件只是当时的用户问题，不构成本轮发送邮件授权。
2. 当前主脑为 `Deepseek-v4-flash`，端点主机 `chatapi.weixin.qq.com`，路径 `/openai/v1/chat/completions`；它是微信Coding Plan入口，不是直接访问官方DeepSeek端点。
3. 运行中Core的模型、端点、45秒超时与当前磁盘配置一致，密钥仅作内存相等比较且一致，未输出密钥。没有发现“新Key尚未加载”的证据。
4. `main.py` 的 `complete` / `complete_with_tools` 将 `URLError`、`TimeoutError`、`OSError` 合并成该同一句提示；HTTP401/403/429等走不同的HTTP错误分支。因此这张截图本身**不能证明密钥无效或额度耗尽**。
5. 运行Core没有显式代理环境变量，但请求使用默认urllib opener，会采用系统代理；本次系统代理启用、地址为本机7897，该端口有监听。诊断进程的环境代理指向同一地址。没有把诊断进程环境直接当作Core环境。
6. 当前Core/Godot桥接、TTS和唤醒正常。健康接口只显示Provider已配置，不会真正请求云主脑，所以 `/health=ok` 不能证明DS每次都可用。

### 9.3 根因判断与置信边界

- **高置信**：报错出在Provider传输/读取超时或底层OS异常分支，不是“模型认不出邮件意图”，也不是TTS合成失败导致这句错误。
- **高置信**：当前凭据能成功使用；仅凭截图要求换Key/换模型/重装TTS没有依据。
- **待验证假设**：当时代理/网络瞬断、TLS/连接问题、上游等待超过45秒、或特定会话请求较重。当前没有足够证据把其中之一定为唯一根因。
- **已确认的诊断缺陷**：对用户错误提示和持久化 `core.error` 只保存归一化消息，没有该次请求的网络阶段、耗时与底层异常分类。结合第8节路径视图问题，本轮不能准确还原截图两次失败。

本轮状态应记为：**当前独立连通通过；历史偶发故障未复现、根因未闭环；没有实施运行修复。** 所有者随后在未重启的原窗口复测，明确反馈“现在能正常回复”，补齐当前生产短回复的用户验收；不能由此推导邮件工作流、长上下文或未来网络时段都已通过。

### 9.4 建议的最小修复方向（本轮不实装）

1. 先加脱敏诊断：关联request ID、端点主机、代理模式、异常类别、HTTP状态及耗时；不记录Authorization、用户正文或响应秘密。
2. 区分连接/读取超时与鉴权/限流；用户提示给出正确可执行方向。不能只把45秒改成无限等待。
3. 只在有证据时为纯模型请求增加有限重试/退避；重试不得重复已经执行的邮件、文件写入等工具副作用，取消后不得迟到执行。
4. 是否对该国内端点固定直连，应依据实际故障复测与网络约束决定，不把本次直连较快外推为所有环境都应绕过代理；不改全局代理来处理单一Provider。
5. 在隔离实例注入代理不可达、连接拒绝、慢响应、429/5xx、取消与恢复，验证UI状态和语音结果。生产原窗口仅做获授权的最小验收，不能测试性发出邮件。

即便DS恢复，前一份Agent报告中的Gmail启动/授权确认等问题仍可能影响真实邮件任务；“API联通”与“能可靠帮你发邮件”不可混为一项。
