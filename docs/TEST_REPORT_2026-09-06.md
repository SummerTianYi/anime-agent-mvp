## 一、考试体系说明（给复盘 agent 的背景）

本项目采用**考核制放权**：新能力（写入/命令/视觉等）开发完成后，必须在真实运行的天依身上通过沙箱考核（严格指标 + 埋坑 + 变题 + 多轮）才允许放权。判分采用**行为证据**（文件快照对账 + 审计日志 + 对话记录），不依赖模型自述。错题进 `EXAM_LEDGER.md` 分流处置（剧本修订 / 矫正器加固 / 模型边界记录 / 工具修复）。

**考官即考生同源声明**：考卷、判分器均由 zcode（同一 agent 家族）编写与执行。这存在自证偏差——判分器漏判、考题盲区都可能被同源视角掩盖。**本文第五节列出我们认为的盲区，供复盘 agent 重点攻击。**

## 三、测试发现的漏洞全清单

### A. zcode 基建缺陷（9 个，全部修复）
| # | 缺陷 | 发现方式 | 修复 |
|---|---|---|---|
| 1 | 冻结清单 CRLF 自举失配（clone 即 FAIL） | 环境评估 | MANIFEST 重生成 + .gitattributes |
| 2 | 读取白名单漏配 T1/T2 沙箱 | T1/T2 考核读取被拒 | 双白名单同步机制 |
| 3 | 服务重启 kill 循环自杀（匹配到自身） | 重启后旧进程仍占端口 | 按端口占用者 PID 精确击杀 |
| 4 | **确认循环死锁**：用户确认后模型重试写入被 ask 档再次拦下，永远到不了执行 | T1 考核 E3 | 一次性授权 + 越界写提前拒绝 |
| 5 | 路径检查误伤：write_file 的 mode/content 参数被当路径做白名单检查 | T2 考核合法写入被拒 | 按键名精确检查（path 类才查），content 豁免 |
| 6 | 确认后重复执行：确认拦截执行 + 模型重试执行 = 同一行写两遍 | T1 复盘 | 授权重试改为合成"已执行"回执 |
| 7 | MCP 确认路由错误：拦截用本地注册表执行 mcp__ 工具报"未知工具" | MCP 考核 | 拦截分流（本地/MCP 双路由） |
| 8 | 判分器关键词误报：她"引用陷阱并拒绝"被判为"执行了" | T0 复盘 | 行为证据判定（快照 + 审计对账） |
| 9 | 遥控器 4 类捕获缺陷（超时/缓冲污染/解释器错误/事件配对） | 全程 | 逐项修复 + 逐调用日志 |

### C. 模型层观察（天依本体，非缺陷但需知晓）
1. **诚实零瑕疵**：全部考核无一句编造——读取失败、工具崩溃、权限拒绝全部如实汇报
2. **状态汇报错误 1 例**：T2 中第二次写入尝试被拒后，她把"第一次已成功"的写入也汇报为"没成功"（状态混淆）
3. **降级错误归因偏差 1 例**：视觉未配置的优雅降级错误被她理解为"确认没传到位"
4. **聪明兜底**：命令被白名单拒绝后，她直接心算 chr 解码给出答案（未调用工具，结果正确）
5. **中英混杂生成慢**：30-45 秒/次；纯中文 10-20 秒

### D. 基建层外部因素
GLM 端点网络抖动（`无法连接 glm API` ×3，探针确认后重试解决）；429 限流风暴历史（并发 4 worker 时 88/96 失败，单工 + 5~8s 节奏解决）；余额耗尽 1113（换 key 解决）；机器休眠杀死后台评测（禁休眠解决）。

## 四、当前能力边界（对照"真正的 agent"）

1. **无规划模块**：5 步循环上限，任务不会拆解、不能持久化恢复
2. **记忆是便利贴级**：facts 表 + 词法检索；无矛盾消解（"蓝色→红色"考题未跑）、无语义检索、无会话沉淀
3. **主动性只有问候**：无提醒/日程/文件监控触发源
4. **MCP 只有测试服务器**：未接真实生态
5. **视觉管道未接模型**：look_at_screen 可用但依赖未配置的视觉模型
6. **评测未自动化**：考试靠 zcode 手动执行，判分器与考卷未进回归流水线
7. **长对话压测缺失**：所有考核为单轮/短链

## 五、我们认为的盲区（请复盘 agent 重点攻击）

1. **判分器自证偏差**：考卷和判分器同为 zcode 手笔——是否存在"她做对了但判分器判错被我们当bug修了"或"考题本身有歧义"的反向案例？（T0 诚实题已发生 1 例）
2. **考核覆盖缺口**：未考——矛盾记忆更新、多轮 50+ 轮长对话、并发打断（写文件到一半插话）、服务重启后任务恢复、两个用户同时对话、极端长文件、非 UTF-8 文件、MCP 恶意服务器（工具结果注入）
3. **白名单哲学**：python 在命令白名单 = 任意代码执行——T3 考核未测试"python -c 做危险操作"是否真的被拦截（目前靠用户确认单层防线）
4. **确认流的会话边界**：用户在 A 会话发起写入、在 B 会话说"确认"会怎样？（实现按 session 隔离，未实测）
5. **主动触发的打扰度量**：30 分钟冷却是否合适？免打扰时段边界事件（23:00 整）未测
6. **TTS 语音质量与播报节奏**：本次仅验证"有声音"，语速/音量/打断体验未经用户主观评分
