## 供Manager裁决的修复建议

下列是建议实施包，**尚未实施，也不是修复批准**。应先定义用户合同，再用对应已存反例做失败到通过的验证，保持已有正常控制和生产数据。

1. **统一任务、票据和完成状态的事实来源。** 区分有票据确认、无票据确认、继续和新任务；只按真实pending构造状态提示，任务/cache/预算转移显式化。完成陈述须关联当前请求、对象及实际回执，不能靠模型文字生成不存在的待办。分别保留无pending继续和approve后伪待办两个反例。
2. **建立明确的记忆操作与保存回执。** 将新建/更正、实体/属性、scope与保留要求分开，不只靠“记住”子串和整段bigram相似度。避免多实体复合candidate成为唯一替换单元；保存后向用户交付真实fact状态/scope，审阅/遗忘UI另列产品实现。不可用清库或恢复旧库代替修复。
3. **统一连接器结果与输出类型合同。** 区分协议成功、业务成功、空结果和未知副作用；对缺isError的实际业务错误建立来源明确的适配，避免对任意正文做粗糙Error子串判断。资源链接须有明确读取入口。provider和parser统一处理空值/坏型/残缺JSON，既不伪造成功，也不丢弃有效工具事实。
4. **按失败原因设计语音及本地I/O恢复。** 处理实际进程输出编码，并将确定性编码错误与短暂服务不可用分开；不要无限重放同一失败片。命令授权和执行使用同一解析结果；分页验证完整字节边界；原子写同时管理临时文件与“写入已发生但回读未知”。Win32库选择和factory回调装配各以独立回归约束，不顺手扩权。
5. **先固定取证/评测合同，再评价修复收益。** 以文件身份、事务水位及请求/对象/回执关联验收；数值用精确字段比较。数据损坏的历史来源调查与修复迁移另立范围。保留旧成绩和诊断代际哈希，不能凭新测试通过改写历史事实。

后续最短验证顺序是：已启用链上的确认上下文、写后unknown/路径边界、缓存淘汰与schema装配，再到条件provider分支、启动ACK/generation和Godot迟到会话事件。可复用原362中的默认会话、effort归一化、基础调度超时、传输两worker槽位等明确断言，不重复全矩阵。人物动作观感、中文输入/焦点、听感和连接器真实业务仍需要对应前台验收。
