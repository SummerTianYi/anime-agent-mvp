## 调度缺陷与修复

原 `speak` 提前创建两个未来片段的准备任务。`_serial_synth` 使用 FIFO 信号量，`_play_part` 得到甲的明确加载失败回执后，重做排在已经等候的丙之后。`_precache_farewell_audio` 还会直接向公共线程池提交合成，旁路了前述信号量。

修后在 Core 保留可撤销的等待名单。选取顺序依次为当前所需段（含明确加载失败的重做）、未来段、告别预缓存。同级按入队顺序。只向专用单线程执行器提交获准的那一项。获准者恢复运行时复核归属和优先级。新回复淘汰旧任务，即使旧任务刚被唤醒也不能拿旧结果发声。HTTP 进入后由实际返回回调释放占位。未来段变为当前需求时，原等待项升优、同一个任务继续。已就绪 WAV 直接复用。每个回复仍只预取一或两段。

| 确定性验证 | 结果 |
|---|---|
| 播放器报告甲的文件加载失败，乙在途，丙等待。观察到甲重做进入队列后才释放乙 | 修前和修后实际 worker 峰值均为 1。修后甲重做成为下一次实际合成。甲只多生成一次，乙和丙各生成一次。最终派发顺序为甲、甲新文件、乙、丙 |
| 预取满、升优与同级顺序 | 乙以未来段优先级入队，从同一个等待项以当前段优先级获准。后续丙先于告别缓存，两个等待的同级缓存按原顺序恢复。另以占满公共线程池的反例验证了专用 worker 和调用上下文 |
| 排队、获准但未提交、执行中、返回后尚未交付时取消 | 对四个窗口分别控制执行器的返回时刻。等待名单最终为空、后继均成功，运行中的等待者取消后占位持续到实际返回 |
| 告别预缓存 | 通过实际 `_precache_farewell_audio` 入口，验证两条缓存让位、恢复、固定到独立目录、内容一致并通知 Avatar。原缓存校验、保存及故障恢复循环沿用 |

## 实际播放

隔离 Core 使用新 SQLite、随机 WebSocket 端口、固定回复和真实 `_speak_reply`。协议转接器只在测试角色与隔离 Core 的真实 Avatar WebSocket 之间转发播放、停止和回执。Godot 自己加载每个真实选中 WAV，运行原每帧角色动画、口型、增益和播放器。首声取输出总线越过 0.003 的帧，完成取回执。每个正常片段都有匹配的真实 Core 落库回执。0 次 DS 或其他模型对话调用。

短答固定为“我在，请讲。”。三段长答固定为：

> 刚才雨停了，窗边有一点阳光。小小的水珠还挂在叶子上。
>
> 书可以慢慢读。我们把最喜欢的那句话夹在蓝色书签里，留给明天。
>
> 等会儿，再一起听听窗外的风吧。

真实对照两侧均使用修后调度。每轮重新合成，保留原有随机采样和自检择优。两次配对采用 1→2、2→1 的顺序。表内时间为毫秒，等待次数指这一篇回复中等文件超过 80 ms 的次数。队列计时分辨率在这台 Windows/Python 3.12 上约为 15.6 ms，表中的 0 含低于时钟分辨率的短等待。

长答第三个边界在两轮里都出现可听差异。第一轮的前段末声到下段首声由 **1400 降到 533 ms**（选中 WAV 边缘静音合计 434 / 474 ms）。第二轮由 **1333 降到 534 ms**（472 / 465 ms）。第二轮双段仍在第一个边界等了 489 ms。实际试听反馈为“听到了，停顿自然”，没有收集按不同模式分别打分的盲听结果。

首声也有代价。第一轮长答首段在单段模式一次通过，双段模式触发重做。两轮短答的单段模式都触发了重做。短答只有一个片段，无法从预取获得调度收益。第二轮两种长答的首声相同。两种预取均未人为攒稿或等待全篇。每种模式只有两个长答样本，已观察到连续性改善，不能据此承诺每次更快或完全无停顿。

### 时序、自检、资源和恢复

- 从固定回复进入语音入口到首个有声混合帧计首声。额外等文件取 `max(0, 下一文件 ready − 上段完成回执到达转接器)`。音频自身边缘停顿另在原始 PCM 上测量，逐文件记录前导、尾随及内部连续至少 80 ms 的低电平区间。实际可听接缝还包含桥接、设备混合、约 33 ms 的帧采样及播放器等待。
- 从第一条到恢复回复完成为 **111.970 秒**。共享服务共 **27 次成功合成请求、37 个 take / 自检、10 次重做**。服务成功计数从 33 到 60，自检任务计数从 34 到 61，重做计数从 16 到 26。所有请求均能与本次固定文本、数值日志、请求 ID、段号和 preparationId 对齐。两次重做仍保留第一份文件，另八次用了第二份（按本请求中新 WAV 的写完顺序与返回路径核对）。报告只保存固定测试文本与指标。音频文件、机器路径和原始日志留在本地。
- 正式 HTTP 接口缺少独立 Whisper 起止时间。实验从本次窗口开始只留数值，记录每个 take 的四段内部合成时长，并测“末组内部合成计时行 → 下一 take 开始或成功标志”的间隔，**690–2884 ms，中位数 764 ms**。这段时间包含自检、WAV 写入、择优和日志轮询。原始记录中 `postSynthIncludingCheckMs` 的含义即此，自检独占耗时未知。
- 资源峰值为整卡已用 **3272 / 8151 MiB**、GPU 利用率 94%。289 次采样中，正式 TTS、隔离角色和隔离 Core 的峰值工作集分别为 **999、469、76 MiB**，系统最低可用物理内存 **471 MiB**。整卡数字含原桌面与其他 GPU 使用者。实验每次 POST 前检查正式 Core 无待播、sidecar 空闲且计数连续，POST 后核对单次增量。前置探针从合成获准到发 POST 用时 71–135 ms。可交付段从 POST 返回到 ready 另用 20–83 ms，均计入实测。采样守护未触发。
- 真实取消时第一段已在发声，Godot 返回 interrupted。第二段的 HTTP 已进入，正常做完并丢弃。第三段未提交，旧语句没有完成事件或额外派发。新回复实际排队 **1485 ms**，随后完成自身一次重做，**4617 ms** 首声并正常结束。整个批次收到 25 个正常播放回执和 1 个取消回执。正式 Core、Godot 和 TTS 使用原 PID，结束回读为 ready。

[全部脱敏原始时序](live.json)含 10 个回合、27 次合成、每次自检数值、准备/派发/回执事件、各边界自然停顿、资源采样及峰值。对照中没有向正式 Core 发聊天消息，正式 sidecar 按原机制生成的测试 WAV 仍由其既有 spool 过期策略管理。
