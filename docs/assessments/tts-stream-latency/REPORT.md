### 整段、分块和停顿的对照

两种播放用同一个既有、已合成的 v2 样本“如果需要我帮忙，就喊我的名字吧。”正常整段测试走正式源码的 _handle_avatar_speak 和 AudioStreamWAV。分块对照用 AudioStreamGenerator，预留 100 毫秒、随后按 20 毫秒小包供给。两次均实际读到 101,760 帧，最后供给前没有观察到跳帧。用户当场反馈“都听到，没有明显断音”。这是相同 PCM 在两种播放路径上的听感，不是已听过原生分块推理生成的另一个 take。

进一步用独立 localhost WebSocket 将同一音频按 40 毫秒源包送入 Godot。第二轮用高精度时钟，开始到 ready 应答往返 **8.20–8.86 毫秒**。两次完整播放（正常、故障后恢复）的首个非静音在接收端 start 后 **66.5、75.2 毫秒**。在两次完整播放中都读到了 EOF 前 Godot generator 的跳过计数 2，局部回调的“0 次”不能代表 IPC 路径。这个指标可能包含启动时的混音周期，无法定位为用户听到两处卡顿。正式协议传的是小 JSON 和本地 WAV 路径，音频文件不会作为 WS 消息上传。实验 WS 发送 PCM 并复用语音总线，往返数值不替代正式桥在真实使用时的单向延迟。[初测](ws-playback.json) · [带接收端首声时间的复测](ws-timed.json)

另一项独立实验只缩短已生成文件末尾的数字零样本。原文件末尾有 **340.84 毫秒**纯零，移去 200 毫秒并核对保留的 PCM 逐字节相同。每种各 8 个段间边界，间隔中位从 **416.7 降到 225.1 毫秒**，缩短约 **192 毫秒**。用户听过两组后的选择为“原来的停顿更自然”。因此不建议在产品中默认剪尾、加速或改变停顿。这个调整也没有缩短模型准备第一句的时间。[样本检查](pause-fixture.json) · [原节奏](gaps.json) · [缩短后](gaps-shortened.json)

### 中断、回执和风险

- 整 WAV 路径验证了正常完成、重复播放 ID 去重、播放中取消、缺文件失败和下一段恢复。取消回执有 interrupted=true，缺文件得到 speech.failed。首次搭建纯音频场景时缺 5 个无关 3D 子节点，Godot 输出初始化诊断，7 项音频断言完成。后续连续播放使用补齐类型的空节点，无需实例化桌宠或连接正式 Core。
- PCM 原型进行了两个批次的实际 localhost/Godot 测试。正常收齐 101,760 帧、耗尽队列后发完成回执；中途取消得到 interrupted；跳过一个序号得到 failed，音频总线还未发声；之后的新 ID 能完整播放。每个终态后都注入迟到片段并重复 start，原型返回同一终态，没有重放。终态由本地播放器缓冲排空与驱动延迟窗口判定，未测试设备拔出、系统睡眠、真实 GPU 计算退出或真实原生块在网络抖动时的尾音。
- 固定上游有 v2Pro 语义分块、说话人嵌入和重叠拼接代码。正式 sidecar 的整选机制最多试听两次，第一条分数低于 0.9 才重做，最后选较好的一条。提前播放第一条的前缀可能让用户听到后来被淘汰的发音。音色是否相同、接缝自然度及原生峰值显存仍需实测；现有听感结果不能迁移到新推理算法。[固定版本上游推理代码](https://github.com/RVC-Boss/GPT-SoVITS/blob/48b1a0169a28582a8984402f82cf438d3bfa6aca/GPT_SoVITS/TTS_infer_pack/TTS.py)

### 下一步最小修改

1. **先在隔离 sidecar 和 Core 加同一 request/part/take 的计时。** 记录模型加载完、首次推理、自检进入/退出、重新采样、选中、下一段准备好、前段播放结束。给出慢回合的逐条轨迹，优先区分用户究竟在等第一句、等自检重做，还是等尚未准备好的下一段。Godot 保留现行增益和停顿，暂不用引入新的播放协议。
2. **保留完整选优，先验证相邻片段的调度。** 现有 Core 已有一段预取。重点测下一段就绪晚于上一段 finished 的差值；只对超时段尝试有界预合成。额外首段延迟的收益待测，不能把消去 200 毫秒纯静音算作有效首声收益。
3. **有空闲的本地测试设备后再运行真正的同权重 A/B。** 用配套 sidecar 脚本分别启动原 WebUI WAV 与 TTS.run 原生 mode 2，保留相同权重、参考、语速、文本和双 take 选择。生产质量对照延迟以“核验选中后可听”为准，未核验首包仅作单独试听。只有 sidecar 原生生成、Core 取消归属、Godot 缓冲/断线回执、显存及盲听都取得证据后，再决定是否动这三层。无法在完整选优前确定最终 take，现阶段建议可承诺的无损首声提速为**未证实**。

### 复现与已有失败

离线运行 `python -B docs/assessments/tts-stream-latency/audit.py` 可核对 DS、WAV、PCM、回执与停顿结果。真实 DS 入口为 [ds_handoff.py](ds_handoff.py)，使用 Core Python 环境、正式源码的独立加载、空测试目录及既有官方 DS 配置，参数为 --core、--scratch、--ds-env、--output。独立库且实际 TTS 客户端入口截断，不向正式 TTS、Godot 或业务发测试请求。

播放测试在私有临时目录使用 config_version=5 的最小 project.godot，复制被测 Godot 项目顶层 .gd 和 .gdshader（含 speech_output.gd）。给 PROBE_WAV 一个合成测试 WAV、PROBE_RESULT 一个新 JSON 路径，设置实验进程 ANIME_AGENT_SPEECH_GAIN_DB=5。用 Godot --display-driver headless --audio-driver WASAPI --max-fps 120 --path FIXTURE --script ABSOLUTE_PLAYBACK_PROBE_GD；PROBE_GAPS=1 切换为连续段实验。每次使用不同输出路径。[播放探针](playback_probe.gd) · [纯零剪尾对照](pause_fixture.py)

[WebSocket 驱动](stream_bridge.py)接受 --wav GENERATED_WAV --godot EXE --project FIXTURE --output RESULTS，使用 Core 环境的 websockets 15.0.1。对原生未自检的隔离预览，用 --live-queue 替代 --wav，配合 sidecar 推理原型 --emit-preview，消费初次长样本在合成时逐块发布的私有队列；应在首块生成前启动接收器，过期队列不能用于首声计时。[Godot PCM 接收器](stream_sink.gd)
