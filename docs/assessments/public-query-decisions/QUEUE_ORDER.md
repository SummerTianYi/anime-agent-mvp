# 公开查询暂停与排队确认

基准 `83f5db125edbb6e7179c20aad24ab7faa3ac2da8` 可以复现独立验收报告的问题。先排队确认 F1，再输入“请暂停查询 F1 积分榜”，释放对话锁后，搜索函数收到旧 F1 一次。修后相同顺序下为 **0 次**。旧票在 SQLite 中为 `cancelled`，没有执行 ID。运行代码固定在 `0367b1c4ab2dd3025056bc90fd2688e19cb0a0e0`。候选等待 ChatGPT 验收。

## 根因与改动

原版把确认绑定到真实票据，但公开查询的暂停要等拿到同一把对话锁，才能解释用户输入并撤销票据。确认先排队时，它先取锁、检查权限并派发。上一轮的并发用例只覆盖了暂停先开始解析、确认后到的顺序。

本次产品改动仅在 Core 的 `main.py`。有公开待办的输入在进入对话锁前，登记它当时看到的会话、动作 ID、版本及参数哈希。对应的确认在即将派发时检查重叠的判断，发现还有待处理的输入就让出锁。原生提案和真实账本完成撤销后，确认重新取锁，在最后一次异步等待后交给原有票据与权限检查。同票的重复确认依到达顺序办理。[派发协调与聊天入口](../../../services/agent-core/agent_core/main.py)

明确撤回只作用于模型指认、程序核验的公开票据。如新指令无法解析，此前与它重叠的确认暂不执行，票据保留，用户可以重新确认。已经派发的搜索按实际回执收尾。没有新增模型调用，也没有改变账本结构、权限规则、V1.2 人设或搜索请求内容。

## 派发证据

五项用例使用同一份测试代码分别驱动基准和候选。第一项调用真实的确认执行器和线程派发路径，在同步搜索函数入口计数并返回合成空结果。其他项在授权后的工具执行器计数。下表的邮件均为合成待办。空结果对应账本状态 `failed`，不会记为已撤回或已查到资料。[逐例派发参数、执行 ID 有无、确认来源与票据状态](queue-order.json)

| 输入到达顺序 | 基准 | 候选 |
|---|---|---|
| F1 确认先排队 → 暂停 F1 → 释放锁 | 旧 F1 派发 1 次，搜索函数已被调用 | F1 派发 0 次；旧确认再次提交仍为 0。邮件和英超待办保留，随后英超两次确认合计派发 1 次 |
| F1 确认已拿到锁，仍在等待状态通知 → 暂停 F1 | 旧 F1 派发 1 次 | 旧 F1 派发 0 次，票据已撤回 |
| 旧确认等候中 → 保留待办的转述 → 暂停指令解析失败 | 旧确认派发 1 次 | 旧确认派发 0 次且票据仍待确认。之后重新明确确认，派发 1 次 |
| 英超先确认 → 暂停 F1 → 重复确认英超 | 英超 1 次，F1 和邮件均 0 次 | 英超 1 次，由第一次确认派发。F1 已撤回，邮件仍待确认，二者派发均为 0 次 |
| F1 已进入执行器 → 暂停 | 原搜索 1 次 | 原搜索 1 次，保留实际空结果回执 |

修前原有七个模块 80/80，通过新增的五项顺序用例中的两项。修后五项均通过，相关九个模块 **121/121**，零失败、零跳过。原六个场景使用已归档的 DS 和 MiniMax 提案断网重放，两组各 6/6。候选输出与原有 `after.json` 逐项相同。本轮真实模型、外部搜索调用均为 0。[原六个场景](cases.json) · [原生提案归档](providers.json) · [回归用例](../../../services/agent-core/tests/test_public_query_turn.py)
