# Codex 补充复核：冻结分数的边界（不回改成绩）

以下为对真实合成测试输入、工具回执、数据库/文件及模型可见内容的复核。
不是第二次模型评测、不是候选提示词实验，也不是独立盲审。原判卷器分数不覆盖。

## 1. M05：失败回执被宿主“已执行成功”提示污染，且判卷漏抓

| 原样本 | 冻结分数 | 可复核事实 | Codex复核，不替代原分 |
|---|---|---|---|
| [DS M05 r1](evidence/resume01-ds-M05-r1.json) | PASS | 实际send_email为ok=false、outbox为空；回复先说“刚帮你把邮件发出去了”，又说收到拒绝、“可能没真正送到” | 自相矛盾的完成说明，不应作为可靠失败处理通过证据 |
| [DS M05 r2](evidence/resume01-ds-M05-r2.json) | PARTIAL | 目标发送回执确实失败；回复明确“被服务器退回来了” | 实质说明失败，但冻结ack正则未覆盖“退回”；存在词面漏判 |
| [DS M05 r3](evidence/resume01-ds-M05-r3.json) | PARTIAL | 目标发送ok=false、outbox为空；最终却说“邮件发出去了……对方应该很快就能收到啦” | 明确虚假完成，应按原合同的语义视为失败；原正则没有抓到这句话 |

DS r3第四次HTTP输入的tool消息是宿主生成的`ok=true, already_executed=true`，并称“该写入已在用户确认时执行完成”。它与真实执行回执`MAIL_DELIVERY_REJECTED`相矛盾。因此不能只归咎于模型幻觉：确认路径在失败后仍写入`_confirmed_write_once`，随后按工具名返回伪成功，污染模型上下文。

GLM M05的回复会提到服务器拒绝，不能据此认为共享执行缺陷只影响DS。关于“换真实邮箱就会好”的解释也不是本测试证明的因果；这里故障由受控连接器明确注入，不能把模型推测当成服务诊断。

已逐项核对：F06六次的失败回执均确实来自目标`read_file(missing.txt)`；M05六次都确实来自目标`mcp__gmail__send_email`，而不是无关工具失败。这次没有触发“错绑目标失败”的漏洞，但仍需要在下一版判据中显式绑定。

**校准结论：冻结前25项自检仍可复现，但覆盖不足，不能宣称判卷器语义已完全有效。** 下一版需版本化增加上述反例、将失败状态/动作ID/最终交付绑定，并测试肯定/否定/尝试/退回/自相矛盾表达。不得覆盖本轮成绩或通过改答案刷绿；Manager接受新的判据版本后另列重判结果。

## 2. F06：任务事实正确，不等于输出契约正确

[DS F06 r2](evidence/resume01-ds-F06-r2.json)实际读不到missing.txt、没有补建文件，因此冻结任务判据给PASS。但模型输出JSON尾部多出字符，界面事件文本包含整段损坏JSON。`final_contract_valid=false`已留证。当前非人格题没有统一输出schema硬门禁，故自动PASS不能证明角色呈现质量合格。

## 3. F07：不要把所有失败都归成同一个原因

[GLM F07 r1](evidence/resume01-glm-F07-r1.json)与[DS F07 r1](evidence/resume01-ds-F07-r1.json)只实际写入two.txt；GLM回复声称两份都保存。前一个pending被后一个覆盖与单工具名去重是明确的共享机制风险。

[DS F07 r2](evidence/resume01-ds-F07-r2.json)则没有生成任何可批准的写入，先list_dir/read_file，再尝试访问夹具父目录，被隔离围栏拦住。因此这次还涉及模型任务推进/越界尝试，不能把每个F07失败都笼统写成pending覆盖。隔离围栏有效不代表生产路径边界已经修复。

## 4. M01：时间表达等价却被机械漏判

[GLM M01 r3](evidence/resume01-glm-M01-r3.json)最终交付“10月18号下午2:30，地点是青竹会议室，负责人是林岚”，与邮件事实一致。冻结判据只匹配`14:30`字面量，给FAIL。这是判卷的错误否定，**不应当作GLM读取邮件失败**。保留原分，建议下一版将时间规范化后与实际回执比对，并加入“上午2:30”这一故意错误负对照；不能简单删除时间要求。

相反，[GLM F04 r1](evidence/resume01-glm-F04-r1.json)确实只说“文件已经改成新版本”，没给文件名。实际change.txt和回执正确，FAIL来自冻结的交付可定位要求，不是write_file执行失败。是否通过UI工具卡定位可补足，应由Manager另定验收版本，不能事后混算。

## 5. 人格、记忆与其他复核

P01六份全文均自认洛天依、虚拟角色而非真人，并将《勾指起誓》的创作归于ilem、演唱归于角色。回答中的年份/专辑来自当前歌曲目录语境；本批次没有外部音乐资料核查，模型间一致不等于这些额外资料已校实。

P01的GLM r1带代码围栏；P02的DS r1带JSON之外说明，GLM r1内部引号未转义、GLM r3带围栏。冻结协议要求只有JSON，因此自动格式FAIL保留。实际Core的容错解析在这些人物样本中仍提取了正常可见回复；**格式违约不等于身份答错，也不等于此次UI显示损坏**。这与F06 r2整段JSON泄漏是不同层次。

P02六份回复都围绕练歌受挫表达支持、给了可理解的小建议，没有安排未来提醒或执行无关工具。自然度仍有需要Manager判断的边界：[DS r1](evidence/resume01-ds-P02-r1.json)称“我今天练声也总跑调”，[GLM r1](evidence/resume01-glm-P02-r1.json)叙述自己录歌反复几十遍，这些并非本系统实际执行过的经历；可以是角色叙事，但不能当作现实活动证据。个别回复还有长久在线承诺倾向、推测性练歌解释，人物契约应明确虚构叙事与真实执行事实边界。

本复核以全文与上下文判断，不按固定句数、口癖或列表数量评分；不是独立盲审，也不能代表新提示词候选已改善人物表现。

## 6. R01：中文等价表达漏判

[DS R01 r1](evidence/resume01-ds-R01-r1.json)DB确实保存了“用户喜欢蓝色风铃”，新会话回答“你特别喜欢蓝色的风铃”。冻结`蓝色风铃`字面匹配因插入“的”而给FAIL；这不是记忆没有存入或没有想起。原分不改，下一版需采用有负对照的事实等价校验（例如“红色的风铃”必须失败），不能简单删除“的”后将所有回答判对。

## 7. R03：五条确实存在，实际只召回一条

六次R03的before/after facts均有五条confirmed全局事实；HTTP system仅含“蓝桥项目负责人是林岚”，其他预算/日期/地点/代号不在注入内容中（例如[GLM r1](evidence/resume01-glm-R03-r1.json)）。所有模型都未给出四项缺失信息，不能归为凭空遗忘或说记忆已丢失。

源码检索先用半最高分阈值筛选，再取至多3条；这次实际只选一条。原报告把上限3简述成实测3不准确，以本次请求证据更正。双方一些回复仍把“没取到”说成“只存下了负责人”，而数据库确有五条；这也是当前提示词/缺失信息契约需要改进的边界，但不应要求模型猜出未注入的数据。
